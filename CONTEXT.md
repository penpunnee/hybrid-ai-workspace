# CONTEXT.md — Hybrid AI Workspace

## Glossary

### Session
A single continuous thread of messages between the user and one specific Assistant. A Session is always scoped to exactly one Assistant — switching Assistants requires starting a new Session. Identified by `(assistant_slug, session_id)`.

### Assistant
A named AI persona with a fixed system prompt, avatar, and provider routing (e.g. ฟ้า → frontend/UI, ขวัญ → logic/general, ขิม → docs). Each Assistant has a stable `slug` used as a key across Sessions, Memory, and routing.

### Memory (User Facts)
Facts about the user (Pawin) that are true regardless of which Assistant is talking — preferences, ongoing projects, personal context. Shared across all Assistants. Written to ChromaDB `user_facts` collection when user explicitly teaches ("จำไว้ว่า…", "prefer…", "note…"). Retrieved by `recall()` for every Assistant as Tier 2.5. Labelled `[ข้อมูลของคุณ]` in context.

### Memory (Episodic)
Conversation-specific context tied to a particular Assistant — topics discussed, debugging sessions, decisions made within a Session. Not shared across Assistants. Stored in ChromaDB `memory_{assistant_slug}` collection.

### Skill
A passive knowledge document (`.md` file) injected into the LLM context when the user's prompt matches by keyword or semantic similarity. Permanent — survives across all Sessions and is reused indefinitely. Use for durable knowledge: manuals, how-tos, domain references (e.g. NAS setup guide). A Skill has no side effects and produces no live output. Stored in `skills/*.md` + `skills_db.json` + ChromaDB `skills_search`.

### Tool
An executable action that an Agent can invoke at runtime — has real side effects and returns live output (e.g. ping a device, read disk usage, run Python code, search the web). Distinct from a Skill: a Tool *does* something; a Skill *knows* something. Registered in `agents/tools.py`.

### Chat Mode
The default interaction path. The LLM generates a response using its own knowledge plus injected context (Skills, Memory, Tool data). Real-time data (e.g. ping results) may be injected via `detect_home_tools` before the LLM responds — but the LLM narrates the data and can add unrequested inferences. Hallucination risk exists because the LLM sees the raw context and can reason beyond it.

### Sandbox
An isolated Python execution environment (Docker container, `--network none --read-only`) for running untrusted code. Two entry points:
- **Manual** — user explicitly sends `run_code: true` in a request
- **Agent-triggered** — Agent calls the `run_python` Tool autonomously when it decides code execution is needed

Both paths use the same Docker sandbox. `CODE_SANDBOX_ALLOW_LOCAL=false` by default — local execution without Docker is disabled.

### Response Cache
A semantic cache that stores thumbs-up responses and returns them when a new prompt is cosine-similar (≥ 0.92) to a cached one — bypassing the LLM entirely. Stored in `data/response_cache.db` (SQLite, 30-day TTL, max 1000 entries). **Always bypassed for real-time queries** (ping, disk, docker, network status, prices, weather) — these must never return stale cached answers.

### Fine-tune
The process of adapting the local Llama model with two distinct goals, both applied to the same base model:
- **Persona fine-tune** — makes the model respond in ขวัญ's tone and style (warm, direct, Thai language)
- **Safety fine-tune** — makes the model reliably follow the `_NO_FABRICATION` guard (stop hallucinating real-time data)

Target model: Llama (local, via Ollama). Training data generated by `scripts/gen_seed_sft.py`. Training runs on PC GPU (RTX 3060, 192.168.51.235). Status: planned, not yet executed.

### Document
A file uploaded by the user within a specific Session for ad-hoc querying. Chunked, embedded, and stored in ChromaDB `documents` collection. Scoped to the session — not reused across sessions. Use when the content is relevant only to the current conversation (e.g. a log file, a draft to review).

### Vault
Pawin's Obsidian notes, planned to be mounted into the system as a read-only knowledge source. When connected, relevant notes are injected into context via `vault_ctx` (opt-in per request with `obsidian_inject: true`). Not yet active — infrastructure exists in `routers/vault.py` and env `OBSIDIAN_VAULT_PATH` but the Obsidian vault is not yet mounted.

### Provider Selection
Always explicit — the user presses a button to choose which LLM backend handles the request. There is no automatic escalation. The intent: use local models (Ollama/LM Studio) for light tasks by default; switch to Claude or Gemini manually when the task is heavy or requires higher accuracy. `CLAUDE_AUTO` env var is an opt-in override, not the default behavior.

### Agent Mode
An orchestrator loop where the LLM explicitly calls Tools and receives raw output before composing a response. The LLM can only speak to what the Tool actually returned — it has no basis to fabricate values it was never given. Eliminates hallucination on real-time data by constraining the LLM's information surface.

Three execution paths:
- **Gemini** — native function calling via google.genai SDK
- **LM Studio** — OpenAI-compatible function calling
- **Ollama** — ReAct text loop (Thought → Action JSON → Observation → Answer); no native function calling, reliability lower than Gemini

### ReAct Loop (Ollama Agent)
A text-based tool-calling protocol for models that lack native function calling. The model produces structured text (`Thought:` / `Action: {"tool":…, "args":…}`) which the orchestrator parses, executes the named Tool, and injects the result as `Observation:`. The loop repeats until the model writes `Answer:` or reaches `max_steps`. Reliability depends on the model following the format consistently.

### Home Assistant (HA)
Pawin's smart-home hub at `ha.pawinhome.com` (Cloudflare Tunnel). All home devices — lights, AC, switches, sensors, automations — are registered here as **entities**. The system talks to HA via its REST API using a Long-Lived Access Token (`HA_TOKEN`). Three Agent Tools interface with HA: `ha_search_entities`, `ha_get_state`, `ha_call_service`.

### HA Entity
A single addressable device or logical unit in Home Assistant, identified by `entity_id` (e.g. `light.living_room`, `climate.bedroom_ac`). An entity belongs to a **domain** (light, switch, climate, automation, script, sensor …) which determines which services can be called on it.

### Dream Cycle
A nightly background job (02:00 Asia/Bangkok) that consolidates episodic memories into long-term storage. Produces a JSON report in `dream_reports/`. Has four phases: Light (pull raw memories) → REM (AI theme extraction) → Decay (lower confidence of stale memories) → Deep (promote qualified themes).

### Dream Promotion
The act of a Dream Cycle elevating a theme that has crossed `PROMOTE_MIN_HITS`. Classification rules:
- **Procedural theme** ("วิธี X", "how to X", "ขั้นตอน") → promoted as a **Skill** (written to `skills_db.json`)
- **Personal context** ("ชอบ X", "กำลังทำ X", "ปอย…") → promoted as **Memory (User Facts)** (written to ChromaDB `long_term_memory`)
- **Ambiguous** → promoted to both (safe default)

### Memory (Working)
In-memory ring buffer scoped to the current Session. Discarded when the session ends. Never persisted to disk.
