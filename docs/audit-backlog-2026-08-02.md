## บทเรียนที่ควรจำจาก audit รอบนี้

1. **บั๊กเดียวกันมักซ่อนอยู่หลายเส้น** — Thai embedding โดน 3 รอบ · "query โดยไม่ดู
   distances" เจอใน 4 โมดูล · แก้เส้นเดียวแล้วคิดว่าจบคือกับดัก
2. **"ตั้งใจยกเว้นไว้ก่อน" = ที่ซ่อนบั๊กชั้นดี** — `utils/documents.py` ถูกยกเว้นตอน
   แก้รอบ ก.ค. แล้วมีบั๊กเดียวกันเป๊ะ รอดมา 3 สัปดาห์
3. **ของในคลังเป็นขยะ แก้ด้วย threshold ไม่ได้** — พอล้าง lessons คะแนนกลับมาปกติเอง
   (คำถามไม่เกี่ยว 0.452 → 0.184) โดยไม่ต้องตั้งเกณฑ์เลย
4. **prompt ที่ให้ตัวอย่างผิด สอนโมเดลผิดทั้งระบบ** — few-shot example เดียวทำให้ได้
   skill ขยะ 60 อันใน 3 เดือน
5. **เทสที่ไม่ได้พิสูจน์ red ก่อน อาจผ่านแบบหลอก** — เจอเอง 2 ครั้ง (ใส่ `client=None`
   แล้วฟังก์ชัน return ตั้งแต่ต้น ไม่เคยเดินถึงโค้ดที่จะเทส)
6. **อ่านโค้ดอย่างเดียวไม่พอ ต้องยิงจริง** — `preferences` มีบั๊กชั้นที่ 5 (collection
   ถูกสร้างด้วย ef ผิด) ที่มองไม่เห็นจากโค้ดเลย เห็นตอน verify บน prod เท่านั้น
7. **อย่า log ว่าสำเร็จโดยไม่เช็คค่าที่ฟังก์ชันคืนมา** — ตกหลุมนี้เองระหว่าง session
   (log "บันทึกแล้ว" ทั้งที่ `save_preference()` คืน False ทุกครั้ง)

8. **`_embedding_function` ที่อ่านจาก client เป็นของหลอก** — chromadb 1.x เก็บ ef ไว้ใน
   collection config แล้วประกอบใหม่ตอน query · `type(col._embedding_function).__name__`
   คืน `DefaultEmbeddingFunction` (384 มิติ) ทั้งที่ query จริงใช้ ollama 768 มิติ
   → เกือบสรุปผิดว่าวัดด้วยโมเดลผิดตัว **วิธีตรวจจริง: ยิง `query_embeddings` มิติที่สงสัย
   ตรงๆ ดูว่า server ปฏิเสธไหม** + อ่าน `col.configuration_json`
9. **local `.env` ไม่มี `EMBEDDING_MODEL` แต่ต่อ ChromaDB ตัวเดียวกับ prod** — สคริปต์ที่รัน
   จาก Mac ถ้าเรียก `get_or_create_collection()` จะสร้าง collection ใหม่ด้วย MiniLM 384
   แล้ว**ฝังถาวร** (แก้ทีหลังต้องลบสร้างใหม่แบบ `preferences`) · รอบนี้รอดเพราะสคริปต์ใช้
   `get_collection()` อย่างเดียว — ควรตั้ง `EMBEDDING_MODEL=paraphrase-multilingual`
   ใน local `.env` ให้ตรง NAS
10. **สมมติฐานของตัวเองต้องถูกวัดเหมือนกัน** — เข้าเซสชันด้วยความเชื่อว่า "ล้างคลังแล้ว
    threshold จะไม่จำเป็น" (อิงบทเรียนข้อ 3) วัดแล้วไม่จริง · และตัวเลขที่วัดได้เองก็ยัง
    เชื่อไม่ได้เพราะ ground truth ที่แต่งขึ้นไม่ดีพอ — **รายงานว่าพิสูจน์ไม่ได้ ดีกว่าตั้งเลข
    จากข้อมูลที่รู้ว่าอ่อน**

## 16. `search_user_facts(min_score=0.6)` — เกณฑ์แน่นเกินจริง (หลักฐาน 2 ชิ้น)

วัดกับ fact จริงบน prod หลัง deploy การสกัดข้อเท็จจริง (2026-08-02):

| fact ในคลัง | คำถาม | score | ผล |
|---|---|---:|---|
| `[การแก้ไข] ไม่ใช่ละ NAS ที่บ้านคือ Synology DS923+ ต่างหาก ไม่ใช่ DS918+` | "NAS ที่บ้านรุ่นอะไร" | 0.645 | ผ่าน |
| ตัวเดียวกัน | "Synology รุ่นไหน" | **0.482** | **ตก ทั้งที่ถามเรื่องเดียวกัน** |
| `เราเตอร์ที่บ้านคือ ASUS RT-BE92U` (สกัดแล้ว) | "เราเตอร์ที่บ้านยี่ห้ออะไร" | **0.447** | **ตก** |
| ตัวเดียวกัน | "อาหารเย็นกินอะไรดี" | 0.108 | ตกถูกแล้ว |

**ผลย้อนแย้งที่ต้องบันทึกไว้:** การสกัดให้เป็นประโยคสั้นสะอาด ทำให้ **recall แย่ลง**
(ข้อความสั้น = จุดยึดให้ embedding น้อย) เรคคอร์ดดิบยาวๆ แบบเดิมได้ 0.645 แต่
ประโยคที่สกัดแล้วได้ 0.447 → ตอนนี้ `user_facts` มีข้อเท็จจริงที่สะอาดแต่**ไม่เคยถูก
ดึงมาใช้** ซึ่งแย่กว่าเดิมในแง่ผลลัพธ์

⚠️ **ยังไม่แก้ตัวเลข** — มีหลักฐานฝั่ง false negative 2 ชิ้นแล้ว แต่คลังมี fact เดียว
จึงวัด precision ไม่ได้เลย ลดเกณฑ์ตอนนี้ = เดาอีกตัวเลขหนึ่งมาแทนตัวเลขที่เดาไว้เดิม
ทางที่ถูกคือทำข้อ 12 (ground truth) ก่อน — คราวนี้มีเหตุผลชัดขึ้นเพราะ **ฟีเจอร์ที่
เพิ่ง verify ว่าทำงานถูกทุกขั้น กลับไม่มีผลจริงเพราะเกณฑ์ตัวเดียว**

ทางเลือกที่ควรพิจารณาตอนทำข้อ 12: `user_facts` เป็น user-taught + verified=True
(confidence 0.9-0.95) ต่างจาก episodic ที่เป็นบทสนทนาทั่วไป — อาจสมควรมีเกณฑ์
คนละตัว ไม่ใช่เลขเดียวกันทั้งระบบ

## 17. ต้นตอร่วมของข้อ 16 + false negative ของข้อ 12 — **embedding dilution** (วินิจฉัยแล้ว 2026-08-02)

เบาะแสจากข้อ 12 ("คำถามแมตช์บทเรียนของตัวเองเป๊ะแต่ได้ 0.49") ไล่จนเจอต้นตอ
**ไม่ใช่ปัญหาของ threshold และไม่ใช่บั๊ก Thai embedding** — โมเดลปกติ (`cos(t,t)`=1.0)

**ชั้นที่ 1 — embedding คือค่าเฉลี่ยของทั้งข้อความ** (คำถาม `"หาข้อมูลการสร้างหน้า ui แชทบอท"`):

| ข้อความที่เอาไป embed | คะแนน |
|---|---:|
| หัวข้อบทเรียนอย่างเดียว | **0.913** |
| + เนื้อ 40 ตัวอักษร | 0.658 |
| + เนื้อ 80 ตัวอักษร | 0.524 |
| doc เต็ม (ที่ระบบใช้จริง) | **0.490** |

อิ่มตัวที่ ~160 ตัวอักษร · เราเก็บ "คำถาม+คำตอบ" เป็นก้อนเดียวแล้วค้นด้วยคำถาม
→ คำตอบที่ยาวกว่ากลบสัญญาณของคำถาม

**ชั้นที่ 2 — ตัวระบุ (รุ่น/รหัส) เป็นสัญญาณรบกวน** (คำถาม `"เราเตอร์ที่บ้านยี่ห้ออะไร"`):

| ข้อความ | คะแนน |
|---|---:|
| `"เราเตอร์ที่บ้านคือยี่ห้อเอซุส"` | **0.789** |
| `"เราเตอร์ที่บ้านคือ"` | 0.606 |
| `"เราเตอร์ที่บ้านคือ ASUS RT-BE92U"` (ของจริงใน user_facts) | **0.447** |
| `"ASUS RT-BE92U"` ล้วนๆ | 0.287 |

สองประโยคที่ต่างกันแค่ชื่อรุ่นได้คะแนนกันเอง **0.496** = โมเดลแทบไม่เข้ารหัสตัวระบุ
**ประชด: ตัวระบุรุ่นคือสิ่งเดียวที่เราอยากจำ แต่เป็นส่วนที่ embedding เก็บได้แย่ที่สุด**
→ อธิบายข้อ 16 ครบ (ทำให้ fact สะอาดขึ้น = recall แย่ลง) และอธิบาย false negative ของข้อ 12

### ทางแก้ที่ทดสอบแล้วกับ ground truth 50 คู่

| กลยุทธ์ | ที่เกณฑ์ 0.60 | หมายเหตุ |
|---|---|---|
| doc เต็ม (ปัจจุบัน) | P=0.94 R=0.89 | |
| กุญแจอย่างเดียว | P=0.75 R=0.83 | ❌ **แย่ลง** |
| **max(กุญแจ, doc เต็ม)** | **P=0.86 R=1.00** | ✅ ได้ false negative คืนครบ |

- **"index แค่กุญแจ" ตกทันที** — 3 คู่แย่ลง (−0.11 ถึง −0.39) เป็นเคสที่คำถามใหม่ไม่ตรงกับ
  คำถามเดิมแต่ตรงกับ**เนื้อคำตอบ** · ค่าเฉลี่ยดีขึ้น +0.183 แต่จำนวนที่ผ่านเกณฑ์**ลดลง**
  (16/18 → 15/18) — **ค่าเฉลี่ยหลอก ต้องนับรายตัว**
- ⚠️ **max ได้ F1=1.00 ที่ 0.625 แต่เชื่อไม่ได้** — ช่องว่างระหว่างกลุ่มกว้างแค่ **0.013**
  (0.634 vs 0.621) = overfit บน 50 คู่ · เชื่อได้แค่ **แนวโน้ม** (recall 1.00 โดย precision ไม่ตก)

### ยังไม่ลงมือ — ต้องตัดสินใจก่อน
เป็นการเปลี่ยนวิธี index (เก็บ 2 vector ต่อ 1 memory) กระทบทั้ง `remember()`/`teach()`/
`save_lesson()` + ต้อง re-index ของเก่า · ทางเลือกเสริม: ตัวระบุ (รุ่น/IP/เลขที่) อาจต้องใช้
keyword/substring match คู่ไปด้วย เพราะ semantic search จับไม่ได้โดยธรรมชาติ
